Create `skills/migrate-vault/SKILL.md` following the exact skill boilerplate pattern from existing skills. The skill must:

**Frontmatter:**
```yaml
- - -
name: migrate-vault
description: Use when migrating the vault to the new PARA-inspired structure. One-time use. Use when user says "migrate vault", "migra vault", "restructure vault", "reestructura vault".
- - -
```

**Step 0 -- Load configuration:**
Standard config.yaml loading pattern. Set VAULT = config.vault_path.

**Step 1 -- Git safety snapshot (per D-14):**
Run `git -C VAULT add -A` then `git -C VAULT commit -m "backup: pre-migration snapshot"`. If commit fails (nothing to commit), continue.

**Step 2 -- Scan current vault state:**
Read config.yaml structure section to discover current paths. For each path, check if the folder/file exists. Build a list of what exists vs what's missing. Also check for files/folders NOT in config that might be in the vault root (to avoid orphans).

**Step 3 -- Build migration plan:**
Using the Migration Map from vault-schema.md, create a plan table:

| Action | From | To | Status |
|--------|------|----|--------|
| Rename | 02 Inbox.md | 00 Inbox.md | exists/missing |
| Rename | 05 Projects | 02 Projects | exists/missing |
| Rename | 09 People | 05 People | exists/missing |
| Move | 08 Resources/meetings | 07 Meetings | exists/missing |
| Move | 08 Resources/knowledge | 08 Knowledge | exists/missing |
| Move | 08 Resources/content-drafts | 10 Content | exists/missing |
| Move | 08 Resources/calendar-cache.md | .cache/calendar-cache.md | exists/missing |
| Move | 08 Resources/granola-processed.md | .cache/granola-processed.md | exists/missing |
| Move | 08 Resources/claude-memory | .cache/claude-memory | exists/missing |
| Rename | 10 Health | 09 Health | exists/missing |
| Create | (new) | 11 Archive | - |
| Create | (new) | .cache | - |

Skip rows where source doesn't exist (graceful degradation). Flag any unexpected items in old folders that won't be moved.

**Step 4 -- Present plan and wait for confirmation:**
Show the migration table to the user. Show count: "X folders to rename, Y folders to move, Z folders to create, W files to move". Ask: "Aplico la migración? (s/n)". Only proceed after explicit confirmation.

**Step 5 -- Execute migration:**
For each row in order:
1. Create target parent directory if it doesn't exist (`mkdir -p`)
2. Move/rename using `mv` (preserves filenames for wikilink safety per Pitfall 4)
3. For moves from 08 Resources/: after all moves, if 08 Resources/ is empty, remove it

**Step 6 -- Add frontmatter to existing notes:**
Scan all .md files in the new locations. For each file:
- If it has no YAML frontmatter, add appropriate schema based on location:
  - Files in 05 People/ get person frontmatter (tags: person, name from filename, created: today, last_interaction: today)
  - Files in 07 Meetings/ get meeting frontmatter (tags: meeting, date: extracted from filename or today, attendees: [], source: manual)
  - Files in 08 Knowledge/ get knowledge frontmatter (tags: knowledge, topic: from filename, last_updated: today, entries: 1, maturity: seed)
- If it already has frontmatter, check for missing required fields and add them with sensible defaults
- Present frontmatter additions for user review before writing

**Step 7 -- Update config files:**
Update both `config.yaml` (user's file) and `config.example.yaml` (git-tracked) structure section with all new paths. This ensures Pitfall 5 is avoided -- both files stay in sync.

New structure values (copy from updated config.example.yaml created in Plan 01):
- inbox: "00 Inbox.md"
- projects: "02 Projects"
- people: "05 People"
- meetings: "07 Meetings"
- knowledge: "08 Knowledge"
- content_drafts: "10 Content"
- content_ideas: "08 Knowledge/content-ideas.md"
- calendar_cache: ".cache/calendar-cache.md"
- granola_processed: ".cache/granola-processed.md"
- claude_memory: ".cache/claude-memory"
- training_log: "09 Health/training-log.md"
- menus: "09 Health/menus"
- archive: "11 Archive"
- cache: ".cache"

Also update tags section in both files to add GTD contexts and status tags (per D-16).

**Step 8 -- Verify migration:**
Read updated config.yaml. For each path in structure, check if it resolves to an existing file/folder in VAULT. Report any paths that don't resolve.

**Step 9 -- Git commit result:**
Run `git -C VAULT add -A` then `git -C VAULT commit -m "feat(vault): migrate to PARA-inspired structure"`.

**Step 10 -- Report:**
Show summary: "Migration complete. X folders renamed, Y folders moved, Z folders created, W notes updated with frontmatter. Run `git log --oneline -5` in your vault to see the backup + migration commits."

**Graceful Degradation table:**
| Missing | Behavior |
|---------|----------|
| Source folder doesn't exist | Skip that move, note in report |
| 08 Resources/ doesn't exist | Skip all moves from Resources |
| File already has frontmatter | Check for missing fields only |
| config.yaml doesn't exist | Update only config.example.yaml, warn user |
| git not initialized in vault | Skip git steps, warn user to backup manually |

**Important Rules:**
- NEVER auto-migrate -- always present plan and wait for confirmation
- NEVER rename files (only folders) -- wikilinks resolve by filename
- NEVER delete source folders until confirmed empty
- Spanish language for all user-facing text
- This is a one-time skill -- can be removed after successful migration
