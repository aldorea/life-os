**Step 0 — Load configuration:**
Standard config.yaml load pattern (same as morning/SKILL.md Step 0). Set `VAULT` = `{config.vault_path}`.

**Overview section:**
Unified sync orchestrator. Runs all configured connectors sequentially in fixed order, collects results, and displays a compact status report. Each connector is independent — if one fails, the rest continue. Non-interactive — never prompts the user.

**Process section:**

**Step 1 — Read connector configuration:**
Read two config sources:
- `${CLAUDE_PLUGIN_ROOT}/config.yaml` for: `calendar.tool`, `training.import_source`
- `VAULT/{config.structure.connectors_config}` (connectors.yaml) for: `jira.projects`, `slack.channels`, `reminders.lists`
- Granola: determined by MCP tool availability, not YAML config

Document clearly which config source applies to each connector (addresses Pitfall 1 from RESEARCH.md).

**Step 2 — Execute connectors (sequential, fixed order per D-05):**

For each of these 6 connectors in this exact order (per D-04, D-06):

2.1 **Calendar**
- Config check: `config.calendar.tool` is NOT "none" and NOT empty
- If configured: Execute sync logic defined in `skills/sync-calendar/SKILL.md`
- Collect result: `{status: "success"|"error"|"skipped", message: "..."}`

2.2 **Jira**
- Config check: `connectors.yaml` has `jira.projects` with at least one entry
- If configured: Execute sync logic defined in `skills/sync-jira/SKILL.md`
- Collect result: `{status: "success"|"error"|"skipped", message: "..."}`

2.3 **Slack**
- Config check: `connectors.yaml` has `slack.channels` with at least one entry
- If configured: Execute sync logic defined in `skills/sync-slack/SKILL.md`

2.4 **Reminders**
- Config check: `connectors.yaml` has `reminders.lists` with at least one entry

2.6 **Training**
- Config check: `config.training.import_source` exists and is not empty
- If configured: Execute sync logic defined in `skills/sync-training/SKILL.md`

- Collect result: `{status: "success"|"error"|"skipped", message: "..."}`

For each connector: DO NOT duplicate the connector's implementation logic. Reference the sync-* SKILL.md as the source of truth. Include a 1-2 sentence summary of what each connector does for context, but delegate the actual sync steps.

Each connector is wrapped in independent error handling — if one fails, log the error as the result message and continue to the next (per USYNC-02, D-05).

**Step 3 — Format and display report (per D-07, D-08, D-09):**
```
Sync completado:

✓ Calendar   — {message}
✓ Jira       — {message}
✓ Slack      — {message}
✗ Reminders  — {message}
✓ Granola    — {message}
─ Training   — {message}

{N} error(es). Revisa {connector names}.
```

Icon rules (D-08):
- `✓` for status = "success"
- `✗` for status = "error"
- `─` for status = "skipped"

Error summary line (D-09): Only show if at least one connector has status "error". Format: `{count} error(es). Revisa {comma-separated names of failed connectors}.`

If zero errors, do NOT show the error summary line.

**Graceful Degradation table:**
Include a table documenting what happens when each connector fails, same pattern as morning/SKILL.md but focused on sync only.

**Important Rules section:**
- Each connector is independent — failure in one NEVER blocks the next
- Non-interactive — never prompt the user for input during /sync
- Spanish language for all user-facing output
- Git safety is inherited from each connector's SKILL.md (do NOT add a separate git layer — addresses Pitfall 5)
- If ALL connectors fail or skip, still display the report showing all failures/skips

**Note on git safety:** Each sync-* SKILL.md already handles its own git commits per D-14 from Phase 1. /sync does NOT add additional git safety wrapping. The git commits happen within each connector's execution.
