# Decision Log — Life OS Adaptive Planning Loop Brief

> Append-only. Every decision, change, and override recorded as the conversation unfolds.

---

## Session: 2026-05-25

### DL-001 — Trigger y scope real
- **Trigger**: Problema de discoverability de skills ("demasiados, difíciles de encontrar")
- **Root cause real**: El sistema no tiene un loop de planificación adaptativa. Sin un workflow claro (clarificar → planificar → ejecutar → registrar → mejorar), los skills no tienen narrativa y parecen arbitrarios.
- **Scope del brief**: Life OS como sistema de planificación adaptativa — no rediseño de UX de skills.

### DL-002 — Scope inicial: trabajo/ordenador
- **Decisión**: El brief se centra en contexto trabajo/ordenador primero. Escalar a personal es roadmap, no MVP.
- **Rationale**: Sito usa el sistema principalmente en terminal/CLI. Empezar donde hay mayor retorno.

### DL-003 — Modelo de registro de actividad
- **Decisión**: Infer + confirm. Sistema infiere actividad del día leyendo Jira/calendario/sync. Presenta resumen al usuario. Usuario confirma y añade lo que falta (interrupciones, bloqueos, contexto).
- **Alternativas descartadas**: (1) log manual puro — demasiada fricción; (2) inferencia silenciosa sin confirmación — pierde contexto cualitativo.

### DL-004 — Filosofía GTD como base
- **Decisión**: GTD como framework de referencia. Principio clave: primero hacer el sistema confiable en lo diario, luego subir la abstracción (daily → weekly → monthly → quarterly).
- **Pain point específico**: Sito falla en el paso Clarify — empieza a ejecutar sin clarificar qué hay realmente que hacer.

### DL-006 — Arquitectura de skills: no rediseño necesario
- **Investigación**: Claude Code recomienda exactly el modelo que ya tiene Life OS — one-skill-per-function, orquestadores que llaman sub-skills internas.
- **Fix real**: Quitar `description:` de todos los sync-* sub-skills → desaparecen del menú. `/sync` es el único comando visible.
- **Conclusión**: El problema de "demasiados skills" es de visibilidad (sub-skills internas que se filtran), no de arquitectura. Fix = 5 minutos.

### DL-005 — Contratienpos como señal, no solo ruido
- **Decisión**: Los contratiempos se registran tipificados (reunión extra, incidente técnico, petición de cliente). El sistema los agrega para detectar patrones recurrentes. Patrón recurrente = señal de problema de diseño, no solo mala suerte.
